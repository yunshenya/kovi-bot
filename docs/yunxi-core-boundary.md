# Core 拥有什么：认知循环的归属与每条边界的理由

**状态：** 当前实现（2026-09-15）。本文记录的是**已经落地的边界**，不是目标规范。
**与其它文档的关系：**

- [`yunxi-core-architecture.md`](yunxi-core-architecture.md) 是**需求文档**——Core 应该是什么、
  分几个阶段、DoD 是什么。
- [`yunxi-affordance-cognitive-io-v8.md`](yunxi-affordance-cognitive-io-v8.md) 是 **V8 协议设计**
  ——环境如何向 Agent 发布上下文与动作空间。
- **本文是决策记录**：一次具体的迁移（"把认知循环搬进 Core，并让它有主体"）之后，边界切在
  哪里，以及**每条边界为什么这么切、否决了哪个替代方案**。判断大多原本只写在 commit message
  和代码注释里，散着；这里收拢。

如果你只想知道"这条规则为什么长这样"，先看本文；想知道"还差什么没做"，看架构文档的状态章节。

## 1. 一句话结论

Core 拥有**认知循环本身**：它怎么走一步、这一步为了什么、试过什么、等了什么、做到哪一步为止、
以及在什么信任档位下可以动手。宿主只负责**声明能力**和**执行**。

```
事件 → 规划 ─┬─ 有工具意图 → 记入工作记忆 → 派发 → 结果变成 follow-up 事件 ─┐
             │                                                              │
             └─ 无工具意图 → 可见回复 / 沉默                                  │
                    ▲                                                         │
                    └──────── 下一轮 PlannerInput 带着目标、试过什么、结果 ──┘
```

## 2. 为什么循环必须在 Core

迁移之前，Core 只提供**单步原语**（取一个事件 → 规划 → 仲裁 → 派发 → 把动作结果变回
follow-up 事件），"循环"由每个宿主各写一份：

- Kovi adapter 的 `run_runtime`（`plugins/model/src/yunxi/bridge.rs`）
- `yunxi-cli` 自己的驱动（`apps/yunxi-cli/src/lib.rs`）

于是**停止条件、取消语义、工具结果的信任判断**都散落在 adapter 里。后果不是风格问题：

- 同一个芸汐在不同身体里行为不同——"她"的耐心、谨慎、什么时候收手，取决于哪个宿主跑她。
- `tools.max_rounds` 这个运维配置项**只作用于遗留路径**，主回复路径实际跑 Core 硬编码的默认值
  （见 §4.3）。配置在骗人。
- 工具效果的信任档位全在宿主，Core 派发 `UseTool` 时是**盲发**——模型幻觉或被注入的工具名
  一路放行，全靠宿主兜。

一句话：**跑循环的那个人，顺带决定了这个 Agent 是什么。** 所以循环的归属不是重构偏好，
是"Core 是否独立存在"这个前提的直接推论。

## 3. 边界一览

| 归 Core | 归宿主 |
| --- | --- |
| 循环拓扑（回合推进、follow-up 编排） | 真实工具的实现与副作用 |
| 停止条件与任务预算语义 | 工具有没有、叫什么、跑不跑得动 |
| 跨回合工作记忆（这一步为了什么、试过什么） | 平台的消息/文件/音视频通道 |
| 预期的登记、归属、结算与回报 | 模型 provider、密钥、采样参数 |
| 效果等级语义与每轮的信任档位 | 每个工具**声明**自己属于哪一级 |
| 执行结果 → 是否达到预期/是否卡住 | 结果的传输与物化 |
| 自我效力的证据与写入时机 | 自我模型的措辞与声音 |
| 提示词之外的一切结构 | 提示词本身（人格、语气、平台话术） |

判据：**"这是认知，还是这个身体的能力？"** 副作用是身体的，判断力是她的。

## 4. 七条归属与理由

### 4.1 循环驱动（`crates/yunxi-core/src/driver.rs`）

`run` / `run_bounded` / `drain` / `drain_observed`；宿主只实现 `CognitiveTurnObserver`。

- **`run` 是常驻驱动**：阻塞在队列上，句柄全 drop 才返回——这是生产形态。
- **`drain` 是静止即返回**：给测试与有界脚手架用。**静止与"下一条消息还没来"在 Core 里不可
  区分**，所以它不能当生产循环；这个区分写在代码注释里，我自己先踩过一次（测试挂死十分钟）。
- `should_process` 被设计成**共享查询**（`&self`，且 Core 会问 1+1+N 次：取出事件时、规划后、
  每个意图派发前）。一开始我按 `&mut self` 写，编译器直接拒绝——这是对的约束：取消判定是一次
  查询，会记录检查历史说明副作用放错了层。
- 钩子是**装箱 future**（`TurnHook<'a>`）而不是 `async fn`：`impl Future` 会让 trait 失去 dyn
  兼容性，而驱动要接受 `&mut dyn CognitiveTurnObserver`。

**否决的方案**：让 Core 提供 `run_task(task)` 那种"跑完一件事"的 API。问题是一件事的边界由
事件决定（follow-up 是事件），而宿主才是产生事件的人——API 会变成"宿主先攒事件再交给 Core"，
等于把循环挪回宿主。

### 4.2 跨回合工作记忆（`crates/yunxi-core/src/working_memory.rs`）

按 trace root 索引的按序历史：`WorkingAttempt`（工具名、参数、结果）与 `WorkingObservation`
（某个预期最后怎么了）交错，`MAX_WORKING_ENTRIES = 16` 条，满了丢最旧的。

- **为什么需要**：跟进轮是**重新进入**规划器的，事件里只有最新那一次结果，会话历史里只有说过
  的话、没有做过的事。做到第三步时前两步已经不在她手里——同一句失败的调用会再试一遍，已经查过
  的东西会当成没查过。
- **顺序**：尝试在**每个意图结算的那一刻**记录，不是轮末批量。非工具意图的派生事件是在派发循环
  内内联喂给 `process_event` 的，批量记录会把"因它而结算的预期"排在"引起它的调用"之前。
  `tests::a_mixed_round_records_the_call_before_the_expectation_it_settles` 守着这条。
- **只记工具意图**：工作记忆记的是"这个任务用工具试过什么"，记消息、提醒、目标会把传输记账
  混进推理轨迹。
- **会话级的消息不进这里**：`PlannerInput.expectation_notes` 单独放 §4.3。

**否决的方案**：把模型自己的话（`response.content`）也记进去。它在宿主的会话上下文里已经有了，
而 Core 里那一轮恰恰是"模型 emits tool_calls、无正文"的路径；为此再加一条 planner→runtime 的
通道，换来的只是重复。**记录要解决的是丢失，不是不全。**

### 4.3 预期：给谁、等多久、怎么回来（`crates/yunxi-core/src/executive/`）

两类生产者，区别很重要：

1. **推导（模型不用做任何事就生效）**：一个计划只要调用工具，就已经在结构上预测了"这个工具会
   跑"。Core 自己推导这条预期。它是这条环路上**唯一一个能真正传到跟进轮**的信号。
2. **声明（只有计划知道）**：`DecisionPlan.expectations`，由宿主的原生函数 `task.declare`
   （`plugins/model/src/yunxi/core_model.rs`）承载。**它是声明，不是动作**——
   `native_calls_to_core_intents` 解析出工具名后第一件事就把它挡掉，有测试钉着。

**归属是这次最关键的判断**：

| 归属 | 谁 | 生命周期 | 结果去哪 |
| --- | --- | --- | --- |
| 任务级 | 推导的工具结果预期 | 随任务生死 | 该任务的工作记忆 |
| **会话级** | **声明的预期**（"我发了消息，等对方回"） | **跨任务** | 该会话的待读队列 → 下一次该会话的 `PlannerInput.expectation_notes` |

会话级是必需的：任务在那一轮就结束了，而"等对方回"恰恰**从那一刻开始**才有意义。绑定到任务会
在它开始有意义的一瞬间把它判成"没发生"。

配套的两个语义：

- **匹配按 scope**（`ExecutiveScope::admits`）。这是一处真 bug 的修复——此前完全忽略 scope，
  一个会话的 `message_received` 预期会被**另一个会话**的消息满足。
- **截止时间是时间问题，不是话题问题**：任何经过运行时的事件都能发现某个预期过期了（否则一个
  安静下来的会话永远不会结算它的预期）；但**匹配**必须是同一话题。

**已知限制**：会话级预期只在"有事件经过"时才会被结算或发现过期。一个彻底安静、宿主也不为它
产生任何 tick 的会话，它的预期会一直挂着——不泄漏内存（队列有界），但也不会被报告。要让它主动
到期，需要宿主为空闲会话产生事件，那是主动行为的范围。

### 4.4 任务预算：停止条件（`RuntimeConfig.task_budget`）

`TaskBudget { max_rounds, max_tool_actions }`，**按轮计数**，不按事件深度。

- **为什么不能按深度**：深度数的是**派生事件**，那是"结果怎么回流"的实现细节；轮才是任务真正
  走过的一步。两者今天碰巧接近，正因为如此才更容易被当成一回事。
- **用尽预算的任务静默收尾**，不报错：预算是安全阀，不是让模型想办法绕过的对手。
- `max_trace_depth` 回到它本来的身份——事件代数的结构性递归边界。
- `tools.max_rounds` 现在真的作用于主回复路径。**对外行为变化**：它默认 10，而回复路径此前实际
  跑 Core 的默认 8，所以默认从 8 变 10；想保持原状就在配置里写 `max_rounds = 8`。

**一个被测试逼出来的语义修正**：信任档位（§4.7）曾经在每个意图上重算，于是同一轮里第一个工具
失败会立刻把第二个也挡掉，破坏"一轮多个工具共享一次跟进"。宿主的原规则是**每轮算一次**；改成
在派发循环之前算好、整轮沿用——**一个 plan 是一步，就该当一步判**。

### 4.5 目标与卡住自检（`DecisionPlan.goal`）

`PlanGoal` 与 `expectations` 同层，是它的补集：`expectations` 说"接下来该发生什么"，goal 说
"这一切是为了什么"。没有 goal 的多步任务只是"一串调用"——**Core 能停，但不能"完成"**。

- **目标在任务形成时定下，此后不能被悄悄替换**（`set_goal_once`）。可以悄悄换掉的目标无法作为
  任何衡量的基准。
- **每一轮都看得见**，宿主渲染在历史最前。
- **卡住自检**：同一次调用连续失败/被拒 `STUCK_FAILURE_RUN = 3` 次，Core 直接告诉她。3 次而不是
  2 次——失败后重试一次是合理的，两次就喊卡住是狼来了；换工具不算重复；一次成功就清零；
  **被拒也算失败**（宿主说"不行"同样是"这条路不通"）。
- **用自然语言而不是结构化谓词**：Core 无法拿"回答明天天气的问题"去匹配事件；硬做成结构化只会
  把模型推进一个它推理得更差的形状（AGENTS.md 第 7 条）。
- **判断"达成/达不成"仍然在模型手里**——这是对的。Core 负责的是保证这个判断有依据（目标稳定、
  历史完整），而不是替它判。

### 4.6 自我效力（`SelfEfficacyEvidence` → `SelfModel.limitations`）

先查证再动手救了这个功能：`limitations` 里那条"我可能犯错"是 `seed_yunxi` 播下的常量
（`with_consolidated` 原样克隆），而且**从未被渲染进任何提示词**。往一个没人读的字段里回写等于
没做。

- **只算她自己的**：`SelfEfficacyEvidence { unfinished_tasks, stuck_tasks }`。**工具报错不算她的**
  ——网络和宿主失败不是她的能力问题，算在她头上会污染自我模型。算她的是：步数用光却什么都没说
  出来（取运行时自己派生的 `MessageSent` 事件），以及反复试同一条失败的路。
- **只有成为模式才写**（阈值 `MIN_UNFINISHED_TASKS_FOR_LIMITATION = 3`），由既有的巩固流程经
  `advance_self_model`（`plugins/model/src/yunxi/mind_runtime.rs`）写入。
- **措辞留在宿主**：那是人格的声音，Core 只提供计数。两条措辞都是**可执行的自知**
  （"步数用光了也还没给出答复"），不是计数器的复述，也不含任何工具名——Core 不知道宿主有哪些
  工具，自我认知也不该知道。
- **列表满时拒绝新增而不是淘汰**：种子局限是"她是谁"，为塞一条机器学来的而悄悄丢掉一条是错的
  取舍。同一句话不会写两遍。

**没走的路**：给 Core 开 `SelfModelStore` 写端口。那会破坏"运行时热路径不做持久化"这条既有约束。
证据走 `MindSnapshotRequest`——运行时本来就每轮构造它。

### 4.7 效果等级与信任（`EffectScope` / `effect_ceiling`）

`EffectScope { ReadOnly, UserScoped, Outbound }` 只描述**波及范围**，不描述"看起来危不危险"——
网页检索和记忆写入都"安全"，但属于不同档。

- **能力声明之外还要声明每个工具**：`ActionDescriptor::tool(name, effect, may_carry_foreign_text)`。
  `UseTool` 能力只说"这个宿主有工具"，管不了一个具体的名字；**未声明的工具 fail-closed**，
  因为未声明的名字与幻觉出来的名字在 Core 眼里没有区别。
- **判据在 Core**：吃过外人写的字 → `UserScoped`；上一步失败或被拒 → `UserScoped`；否则
  `Outbound`。会话级判断，因为它描述的是"这个任务现在还能做什么"。
- **下发口径与执行口径同源**：`PlannerInput.effect_ceiling` 交给宿主决定下发什么，宿主不再自己算
  一份。此前同一件事被算了两遍且规则不同，于是**下发给她的工具集**和**真正会执行的工具集**可以
  不一致。
- **宿主只剩一个自己的判断**：只因"她可能想发图"才带 `sticker.list` 的回合。那不是信任判断，
  是"这一轮只打算给她一个只读工具"的下发决定，Core 看不到也不该看到。

## 5. 明确没做的（开放问题）

1. **提示词仍然是宿主的**。人格、语气、平台话术留在 `plugins/model`；Core 只提供人格的**投影**
   （Mind snapshot、目标、历史）。这是有意的——AGENTS.md 第 6 条：人格属于允许常驻的三类之一，
   而它由宿主组织更合适。
2. **会话级预期不会主动到期**（§4.3 末）。
3. **遗留路径仍是遗留**。`memory_query.rs` 与 `qq_call/session.rs` 各有自己的多轮工具循环，服务于
   Core 未接管的能力。它们没有被统一，因为它们不跑 Core 那条链路。
4. **`yunxi-cli` 只证明离线边界**，不是真实第二宿主验收（架构文档 §137.4）。

## 6. 这些判断是怎么验证的

- **端到端优先**：跨任务预期、工具效果档位、任务预算、自我效力，每条都有一个跑完整个循环的测试，
  而不是只测单元。
- **变异验证**：关键修复在提交前把实现改回错误版本，确认测试**真的变红**，再改回来。做过变异的
  包括：D1 终结哨兵、工具效果降档、轮次预算、工作记忆顺序、`Expectation` 的 `trace_root`
  不落库。理由很简单：一个变绿的测试，要么用变异证明它在守东西，要么它可能什么都没守。
- **外部审计**：驱动/工作记忆/预期那一批改动交由独立视角复审，报出的缺陷逐条复核后修掉
  （`d12a6ea`），其中一条是"文档描述的调用次数与实现对不上"——文档错也是缺陷。

## 7. 变更本文的规矩

这份文档只记录**已经落地**的边界。目标规范进 `yunxi-core-architecture.md`；协议设计进 V8 文档。
改变一条边界时，同时改这里对应的理由段——**理由和实现一起改，至少不会漂**。
